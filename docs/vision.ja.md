# Zig_80：ビジョンとアーキテクチャの方向性

[English](vision.md)

## この文書の位置付け

この文書は、Zig_80 が長期的に目指す方向と、その背景にある設計思想を共有するための構想資料です。実装仕様、確定した計画、互換性の保証を定めるものではありません。

ここで述べる構成の多くは現時点では構想段階にあり、まだ設計途中です。技術的な検証やプロジェクトの成熟に伴い、今後変更される可能性があります。

## 目的

Zig_80 は、Z80 という1980年代のCPUを、現代的な開発環境である Zig から学び、プログラムを開発し、将来的には実機へ展開するための統合環境を目指しています。

中心に置くのは、単独のエミュレーターやアセンブラではなく、ひとつの Z80 プログラムを「書く、変換する、動かす、観察する、実機へ届ける」という連続した体験です。ソフトウェアとハードウェアを別々の題材として扱うのではなく、共通の Machine を境界として結び付けることを、一つの方向性として検討しています。

完成した機能を利用することだけでなく、それぞれがどのように成立しているかを追えることも重視します。Z80 を知らない人がレジスタや命令から入り、エミュレーター、ツールチェーン、周辺回路へ段階的に理解を広げられる環境が将来像です。

## なぜZ80なのか

Z80 は長い歴史を持ち、パーソナルコンピューター、ゲーム機、組み込み機器など幅広い領域で使われてきたCPUです。その背景をたどることは、現在の計算機へつながる基本概念を学ぶ入口になります。

現代のプロセッサと比べて観察すべき状態が限られ、命令の取得、デコード、実行、フラグ更新という流れを比較的直接的に捉えられます。命令セットには固有の複雑さもありますが、少数の命令から学習を始め、段階的に対象を広げやすい点に価値があります。

また、Z80 の再現はエミュレーター実装の教材になります。レジスタ、アドレス空間、スタック、割り込み、実行時間といった要素を、小さな単位から検討できます。物理的なバスを持つ実CPUを入手でき、比較的単純な周辺回路から実験を始められるため、ソフトウェア上の理解を自作ハードウェアへ接続しやすいことも選択理由の一つです。

Zig_80 は、Z80 を単に古いCPUとして保存するのではなく、計算機の基本構造を可視化できる共通言語として扱うことを目指しています。

## なぜZigなのか

Zig は、ホスト上の開発ツールと組み込み向けソフトウェアを、近い考え方で記述できる可能性を持っています。

- クロスコンパイルを言語とツールチェーンの中心に置いており、CLIから異なるマイコン環境へ対象を広げる構想と相性があります。
- メモリ確保と所有関係が明示的であり、CPU状態や固定長メモリを扱うエミュレーターの設計意図を表現しやすいと考えています。
- ランタイムへの暗黙の依存を抑えられるため、組み込みファームウェアも将来的な対象として検討できます。
- `comptime` は、命令情報や静的な表現の整合性を検証する手段になり得ます。ただし、教材としての読みやすさとの均衡が必要です。
- 単一バイナリのCLIツールを構成しやすく、アセンブル、実行、解析といった操作をまとめる用途に適しています。
- ビット、整数幅、メモリ配置を明示して扱えることは、エミュレーターと周辺機器のモデル化に有用です。

これらは特定の実装方式を確定するものではありません。Zig の進化や対象プラットフォームの制約を踏まえ、適用範囲は今後検討していきます。

## Zig_80が目指すもの

Zig_80 が目指す統合環境には、相互に関係する複数の側面があります。

### 学習環境

命令の実行によって、レジスタ、フラグ、メモリ、実行位置がどう変化するかを観察し、CPUの働きを理解できる環境を目指しています。抽象化によって内部状態を隠し切るのではなく、必要に応じて境界を開いて確認できることを重視します。

### エミュレーター

Z80 の振る舞いをソフトウェア上で再現し、実機がなくても試行錯誤できることを目指しています。正確さは重要ですが、学習可能な構造や検証方法も同じく重要です。将来的な精度の範囲は、段階的に定義される想定です。

### アセンブラ

外部ツールだけに依存せず、ソースから自分のROMを生成する過程を理解できることを目指しています。構文解析、シンボル解決、命令エンコードは、言語処理系を学ぶ題材にもなります。

### デバッグ環境

プログラムを停止し、レジスタやメモリを観察しながら一命令ずつ進められる環境を目指しています。将来的には、CLI、TUI、実機デバッグの間で、可能な限り共通した観察モデルを持つことを検討しています。

### ゲーム開発環境

小さな画面、入力、音、時間という制約の中で、簡単なゲームやデモを作れる環境を目指しています。大規模なゲームエンジンではなく、CPUと周辺機器の関係を理解できる小さなSDKという方向性を想定しています。

### 実機開発

エミュレーターで作ったROMを実機へ転送し、同じプログラムを本物のZ80で動かせる状態を長期的に目指しています。この接続が、Zig_80 を単一用途のソフトウェアではなく開発環境として捉える中心的な考え方です。

## 最終的な世界観

```text
            Zig
             │
   ┌─────────┼─────────┐
   │         │         │
Assembler Emulator Debugger
   │         │         │
   └─────────┼─────────┘
             │
        Z80 Program
             │
      ┌──────┴──────┐
      │             │
 CLI Emulator   Real Hardware
```

Zig で作られるツール群は、共通の Z80 Program を中心に協調します。アセンブラがROMを生成し、エミュレーターが実行環境を提供し、デバッガーが状態を観察します。そのROMはCLI上だけの成果物ではなく、将来的には実機でも動作するものとして位置付けたいと考えています。

この図はコンポーネントの実装関係を規定するものではありません。重要なのは、各ツールが独自の閉じた世界を作るのではなく、同じプログラムと Machine の意味を共有することです。

## エミュレーターから実機へ

初期の探索は、再現性が高く、観察しやすいCLIエミュレーターを中心に進むと考えています。実機がなくても命令やメモリマップを試し、問題を切り分けられるためです。

長期的には、その環境を実機PCBへ発展させることを目指しています。ここで重視するのは、エミュレーター向けに書いたプログラムを実機向けに作り直すのではなく、同じROMがそのまま実機でも動くという思想です。

完全に同一の挙動を保証するためには、タイミング、初期状態、未定義動作、周辺機器の差異など多くの課題があります。したがって現時点では互換性を保証するものではなく、Machine仕様を段階的に明文化し、双方を同じ契約へ近づける方向を検討しています。

## 実機構想

実機は現時点では将来構想であり、具体的な製造計画や採用部品を決定したものではありません。一つの方向性として、本物のZ80をCPUに使用し、その周辺回路を現代のマイコンが担当する構成を考えています。

マイコンは、Z80から見たチップセットをソフトウェアで実装します。候補となる役割には、次のものがあります。

- RAM
- ROM
- Video
- Input
- Audio
- Timer
- Storage
- USB Debug

Z80 がアドレスバスや制御信号を通してアクセスすると、マイコンが対象のメモリまたは仮想デバイスとして応答する構想です。これにより、古典的なCPUの実行主体としての性質を保ちながら、表示、記憶、転送、デバッグには現代的な柔軟性を持たせられる可能性があります。

一方で、バスのタイミング、電気的条件、マイコンの応答時間は慎重な検証を必要とします。この構成が最終形になるとは限らず、専用ロジックや追加部品を併用する可能性もあります。

## Zig Firmwareの方向性

将来的には、周辺回路を担当するマイコンのファームウェアも Zig で記述する構想があります。

```text
Zig
│
├─ CLI Emulator
├─ Assembler
├─ Debugger
└─ Firmware
      │
      ▼
    Real Z80
```

ホスト側ツールとファームウェアが同じ言語を共有できれば、データ形式、テストの考え方、Machine仕様の表現を近づけられる可能性があります。また、Zig を学ぶ対象がCLI開発から組み込みへ自然に広がります。

ただし、対象マイコン、Zig の組み込み対応状況、リアルタイム性などは未評価の部分が多く、現時点では構想段階です。コードの直接共有を目的化せず、意味と契約を共有することを優先したいと考えています。

## 共通Machine仕様

CLI版と実機版の間では、共通の Machine仕様を持つことを目指しています。Machine はZ80から観察できるコンピューター全体の契約であり、少なくとも次の概念を含む可能性があります。

- Memory Map
- ROMとRAMの役割
- VRAMの配置と画素表現
- Inputのビット表現
- Timerやフレーム状態
- 将来追加される仮想周辺機器

エミュレーターはこの契約をソフトウェアとして再現し、実機側のマイコンはバス上で同じ意味を提供します。Z80プログラムは実行場所を意識せず、定められたアドレスや状態を利用する、という関係を目指します。

Machine仕様はまだ確定していません。バージョン管理、互換性の範囲、実機固有機能の扱いなどは、今後詳細化が必要です。

## 目指す開発体験

目指す開発の流れは、次のようなものです。

```text
ASMを書く

↓

ROM生成

↓

CLIで実行

↓

デバッグ

↓

実機へ転送

↓

同じROMが動く
```

CLIでは、短い反復時間と詳細な観察を提供します。十分に確認したROMを実機へ転送すると、本物のZ80が同じ命令列を実行します。問題が発生した場合には、CLIと実機の状態を同じ概念で比較できることが理想です。

この体験では、実機への転送を開発の終点とは考えません。エミュレーターと実機を往復しながら、ソフトウェアの誤り、Machine仕様の曖昧さ、物理的な制約を学ぶ循環を想定しています。

## 教材としての価値

Zig_80 は、完成したゲームを効率よく作ることだけを目的としていません。ツールと実行環境そのものを学習対象として扱います。

- CPUでは、命令、レジスタ、フラグ、スタック、割り込み、実行時間を学べます。
- アセンブラでは、字句と構文、式、シンボル、再配置、機械語表現を学べます。
- エミュレーターでは、状態機械、デコード、検証、抽象化されたBusを学べます。
- デバッガーでは、プログラムの観察可能性と開発ツールの役割を学べます。
- ハードウェアでは、メモリマップ、バス、信号、タイミング、周辺回路を学べます。
- Zigでは、明示的なデータ表現、メモリ管理、ホストと組み込みの違いを学べます。

すべてを一度に隠蔽した統合環境ではなく、利用者が関心に応じて一層ずつ内部へ降りられる構成を目指しています。教材としての価値を保つため、過度な抽象化や自動化が理解を妨げないかを継続的に検討する必要があります。

## 将来的に考えられる方向性

以下は実装予定を示すリストではなく、将来的に考えている方向性です。順序、範囲、実現可能性はいずれも未確定です。

- 完全なZ80エミュレーター
- より広い言語機能を持つアセンブラ
- CLIと実機を横断するデバッガー
- 状態を継続的に観察できるTUI
- 小さなゲームSDK
- Video、Input、Audio、Storageなどの仮想周辺機器
- 本物のZ80を搭載したオリジナルPCB
- マイコン向けZig Firmware
- USB Debugger
- 実機とCLIで共有できるROMとMachine仕様
- ブラウザーで学習や共有を行うWebAssembly版

これらは独立した目標ではありません。共通ROMを中心に、学習、開発、観察、実機という体験を一貫させられるかどうかが、方向を選ぶ基準になります。

## 将来の設計判断における原則

将来の設計判断では、次の原則を指針として検討します。

1. Z80プログラムを中心に置き、ツール固有の閉じた形式へ不要に依存させないこと。
2. CLI版と実機版の間で、Machineの意味を可能な限り共有すること。
3. 正確さを追求しながら、学習者が処理を追える構造を保つこと。
4. 小さく検証可能な段階を積み重ね、構想と実装済みの状態を区別すること。
5. 古典的な計算機の制約を尊重しつつ、現代的な開発支援を活用すること。

Zig_80 の最終形はまだ定まっていません。この文書は固定された到達点ではなく、プロジェクトが何を大切にして方向を選ぶかを共有するための基準です。
